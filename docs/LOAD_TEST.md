Generated by `scripts/load_report.py` from Locust CSVs and the API's own `ops_metrics` rows. Target: 500 requests/s for 5 minutes against `POST /v1/score` on the local compose stack, real Win64 test-week feature records (`make load-bodies`), all rings on production (no paired scoring).

- **Client side** (Locust): what a caller saw, including HTTP and JSON (a Win64 body is ~2,500 numbers).
- **Server side** (`ops_metrics`, 10-second buckets): the API's handler time, which the p99 alert watches. Steady state only (first 30 s of ramp-up skipped).

## Metrics recorder cost

Per request the API makes 2 counter updates and 1 latency sample. Timed over 200,000 requests with a writer thread draining every 10 ms (1,000x more often than in production) for lock contention: mean **9.94 µs**, p50 5.80 µs, p99 42.22 µs, max 14001 µs per request (Python 3.11.18). Budget: under 1 ms (1,000 µs).

## Result: the target is not met on this machine

The API never reached 500 req/s, and its p99 stayed above 20 ms in every 10-second bucket of every run. The p99 alert fired for real in each run. The other numbers held throughout:

- every request got an answer (0 failures, 0 server errors);
- no lineage or metrics row was lost;
- throughput rose 2.4x (125 to 306 req/s) through the two fixes below.

Caller-side latency is in seconds because requests waited in the queue: the API was saturated.

The project owner decided (2026-11-24) to record these measured numbers rather than keep tuning.

## Where the time goes (`make profile-api`)

Real production models, in-process, 1,000 requests, no network. Per request:

| Step | Mean | p99 |
|---|---|---|
| Decode the 20 KB JSON body (stdlib `json.loads`) | 0.73 ms | 2.01 ms |
| Validate the request | 0.28 ms | 0.92 ms |
| Build the feature array | 0.14 ms | 0.34 ms |
| LightGBM score (Win64 v1: 1,000 trees, 2,538 features, 1 thread) | 1.28 ms | 2.44 ms |
| Handler time without contention (from the recorder) | 1.91 ms (p50) | 3.35 ms |

Through the full ASGI app, a request cost **7.9 ms of CPU**, of which only about 1.3 ms is the model. The rest is framework work.

Under load, one uvicorn process serves everything (requests, lineage writer, span exporter) under one Python GIL. It saturated at about 125 req/s, about 8 ms of CPU each. Handler time grew from 1.9 ms to 9.7 ms p50 as threads waited for the GIL.

## What was changed (before / after in the table)

1. **4 API worker processes** (`configs/serving.yaml` `workers`, started by `python -m sentinel.serving.serve`). Result: 203 req/s.
   - Memory: 1.3 GB for 4 workers, against 0.4 GB for 1.
   - Each worker loads its own models and writes its own metrics rows. Every reader aggregates them.
   - The registry poll went from 30 s to 5 s, so all workers follow a kill switch, not only the one that received it. The kill-switch CLI now waits until every worker reports production.
2. **C HTTP parser and event loop** (`httptools`, `uvloop`; uvicorn previously fell back to pure-Python h11/asyncio).
3. **One-pass body validation** with pydantic's JSON validator.
   - It replaced FastAPI's default: stdlib `json.loads`, then validation of the Python objects.
   - Decode plus validate went from about 1.5-2.5 ms to 0.30 ms per request.
   - Bad bodies still get HTTP 422; the unit tests are unchanged.

   With 2 and 3: **306 req/s**.

"Batched writes" and "warm-up" from the plan were already in place: lineage is written in 500-row batches by a background thread, and models are warmed before they serve.

## Why it stops here

During the runs the API used about 4.7 of the machine's 8 cores. The rest went to the other 12 containers and the load generator itself:

- MLflow, about 0.4 core, partly the 4 workers polling the registry every 5 s;
- Locust, about 0.6;
- PostgreSQL, Jaeger, Redpanda, the consumers and the dashboard.

The "server" latency above is therefore mostly time spent waiting for a CPU, not scoring.

Not tried, by decision:
- sampling traces of requests that arrive without a caller trace (stream events would stay fully traced);
- more than 4 workers.

On a host where the API has its own cores, throughput should scale with the worker count, at about 8 ms of CPU per request. That is an estimate from these measurements, not a measured result.

## Caveats

- **A stray process during the first two runs.** A leftover unit-test container (a hung run from earlier the same day) used about 20% of one core during the 1-worker and 4-worker runs and during the Stage 8 replay. It was found and stopped before the third run. This is small next to a GIL-bound single process, but the third run had slightly more CPU available.
- **MLflow connection resets at start-up.** The 4 workers loading models at the same moment caused "connection reset" retries against the single-process MLflow server. All loads succeeded on retry.
- **Load-test traffic in lineage.** Load-test rows sit in `predictions` under tenants `loadtest-*`. They have no `event_id`, so the gate and the replay counts never pair them with stream events.
- **What the bench measures.** The metrics-recorder bench times the recorder alone. Its single 14 ms worst case (1 in 200,000 calls) is a scheduler or garbage-collector pause, not the recorder's normal cost.
